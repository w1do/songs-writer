## Context

Код проекта ещё не написан (см. `AGENTS.md`). Стек и дерево проекта зафиксированы в `STRUCTURE.md`: React/Vite/TS/Tailwind/shadcn на фронтенде, FastAPI/SQLAlchemy/PostgreSQL на бэкенде, три таблицы (`songs`, `messages`, `presets`), три сервиса в Docker Compose. По явному запросу пользователя в проект добавляется сущность `presets` (пресеты жанров) поверх ранее зафиксированных `songs`/`messages`. См. `proposal.md` — Why / What Changes для мотивации и границ MVP.

## Goals / Non-Goals

**Goals:**
- Описать единый модуль интеграции с PolzaAi, переиспользуемый всеми AI-функциями.
- Зафиксировать схему данных `songs`/`messages`/`presets` через SQLAlchemy ORM-модели и формат JSONB-полей (`track_settings`, `analysis`, `generation_settings`).
- Описать Pydantic-схемы запросов/ответов для всех FastAPI-эндпоинтов, включая CRUD пресетов, как единый слой валидации на границе API.
- Определить, как контекст песни (idea, жанр, BPM, emotion, lyrics) и выбранный пресет жанра автоматически попадают в промпт каждой AI-функции.
- Определить способ валидации и логирования AI-ответов без повреждения данных песни при ошибке.

**Non-Goals:**
- Не проектируется обработка или генерация аудио.
- Не вводится очередь задач, кэш или отдельный AI-микросервис — единственный вызов происходит синхронно из FastAPI-роутера в рамках одного запроса.
- Не проектируется система ролей/многопользовательская авторизация — только одна пара учётных данных администратора.

## Decisions

### Единый AI-клиент в `backend/app/services/ai.py`
`services/ai.py` инкапсулирует OpenAI-совместимый клиент к PolzaAi (конечная точка и ключ — из `config.py`/окружения), конфигурируется моделью `claude-haiku-5.5`. Все обработчики в `ai.py` (роутер) вызывают функции этого сервиса, а не создают клиент самостоятельно. Альтернатива — создавать клиент в каждом обработчике — отклонена, так как дублирует конфигурацию и усложняет замену провайдера.

### Сборка контекста песни как общая функция
`services/ai.py` предоставляет функцию `build_song_context(song)`, собирающую idea, lyrics, analysis (жанр, BPM, emotion, structure) в единый текстовый/структурированный контекст, добавляемый к системному или пользовательскому промпту каждой AI-функции. Это гарантирует консистентность контекста без копирования логики сборки в каждый обработчик.

### Pydantic-схемы ответа на каждую AI-функцию
Для каждой AI-функции (`IdeaAnalysisResponse`, `LineActionResponse`, `HookResponse`, `ChorusResponse`, `StructureSuggestionResponse`, `FinishSongResponse`, `PrepareTrackResponse`) в `schemas.py` определяется строгая Pydantic-модель. Ответ провайдера парсится как JSON и валидируется этой моделью; при ошибке валидации возвращается HTTP 502 с сообщением, песня не изменяется. Alternative — слабая валидация (проверка только наличия ключей) — отклонена, так как не гарантирует консистентность и ломает frontend.

### Хранение данных только в `songs`/`generation_settings`/`analysis`/`track_settings` (JSONB)
Вместо отдельных таблиц для секций/строк/хуков (запрещено `AGENTS.md`) структура секций хранится как часть текста `lyrics` (с маркерами `[VERSE]`, `[CHORUS]`), а анализ/настройки — как JSONB-поля `songs`. Это соответствует `STRUCTURE.md` и минимизирует схему БД.

### Таблица `presets` как SQLAlchemy ORM-модель `Preset`
Пресеты жанров хранятся в отдельной таблице `presets` (ORM-модель `Preset` в `models.py`): `id` (UUID), `name`, `genre`, `bpm_min`, `bpm_max`, `energy`, `style_prompt`, `negative_style_prompt`, `sound_scene`, `hooks_prompt`, `effects_prompt` (даблы/аэры-адлибы/ревербы как текстовая подсказка или JSONB-структура), `chorus_vocal_style`, `description`, `created_at`, `updated_at`. Пресет по сути — цельный JSON-документ стиля звучания, используемый как единое целое, а не набор жёстких правил. `songs` получает nullable внешний ключ `preset_id` (SQLAlchemy `ForeignKey("presets.id", ondelete="SET NULL")`) — удаление пресета не удаляет песню и не ломает уже скопированные в `analysis`/`track_settings` значения. Отдельная таблица выбрана вместо JSONB-поля в `songs`, так как пресеты — переиспользуемые самостоятельные сущности с собственным CRUD, а не одноразовые данные одной песни.

### CRUD пресетов через `backend/app/presets.py` + Pydantic
Роутер `presets.py` реализует `POST/GET/PATCH/DELETE /presets` поверх SQLAlchemy-сессии (`database.py`), используя Pydantic-схемы `PresetCreate`, `PresetUpdate`, `PresetRead` в `schemas.py` для валидации запросов и сериализации ответов. Эндпоинты защищены той же session-зависимостью, что и `songs.py`/`ai.py`. При создании/обновлении песни `preset_id` валидируется Pydantic-схемой песни и проверяется на существование в БД перед сохранением.

### Пресет как часть контекста, а не хардкод жанровых правил
`build_song_context(song)` в `services/ai.py` расширяется: если у песни указан `preset_id`, функция подгружает связанный `Preset` через ORM-связь (`relationship`) и добавляет его жанр/BPM-диапазон/энергию/style-подсказки/сцену звучания/хуки/эффекты/стиль припевов в собираемый контекст промпта наравне с данными самой песни. Жанровые правила не зашиваются в код как ветвления логики — это соответствует требованию `AGENTS.md` «не хардкодить жанровые правила как ограничения».

### Кнопки copy style/negative style на странице редактора
Под текстом в редакторе (frontend) размещаются три независимые кнопки copy: lyrics, style-подсказка и negative style-подсказка. Источник значений для style/negative style — `track_settings` песни, если они заполнены (например, после Prepare Track или ручного редактирования), иначе значения связанного пресета (`style_prompt`/`negative_style_prompt`). Это позволяет сразу после написания текста скопировать текст и стиль для вставки во внешний сервис генерации музыки (например, SUNO) без перехода на отдельный экран Prepare Track.

### Логирование через `messages`
Каждый вызов AI-функции создаёт одну или две записи в `messages` (role=`user` с собранным промптом или кратким summary запроса, role=`assistant` с сырым ответом провайдера), связанные с `song_id`. Это даёт историю для отладки без отдельной подсистемы логирования.

### Единая сессия через `SESSION_SECRET`
`auth.py` реализует вход по `ADMIN_EMAIL`/`ADMIN_PASSWORD` и выдаёт подписанную cookie-сессию на основе `SESSION_SECRET`; все остальные роутеры используют общую FastAPI-зависимость (dependency) проверки сессии. Простая cookie-сессия выбрана вместо JWT/OAuth, так как пользователь один и регистрация не нужна.

### UI-компоненты только из shadcn/ui
Весь интерфейс (`frontend/src/components`, `frontend/src/pages`) строится на компонентах библиотеки shadcn/ui (устанавливается через `shadcn` CLI поверх Tailwind, как зафиксировано в `STRUCTURE.md`): экран входа — `Form`, `Input`, `Button`, `Card`; редактор — `Textarea`/`ContentEditable`-обёртка, `Tabs` или `Accordion` для секций, `Button` для панели AI-действий; панель предложений AI — `Popover`/`Sheet` или `Dialog` с `Card` для вариантов; sidebar анализа и выбор пресета — `Select`, `Combobox`, `Input`, `Badge`; индикатор автосохранения — `Badge`/`Toast` (через `Sonner`/`use-toast` из shadcn/ui); кнопки copy под редактором и экран Prepare Track — `Button`, `Textarea`, `Separator`. Самописные low-level UI-примитивы (кнопки, инпуты, модалки, селекты) не создаются — используются только компоненты, сгенерированные shadcn/ui, кастомизируемые через Tailwind-классы и `tailwind.config`.

## Risks / Trade-offs

- [PolzaAi недоступен или медленный] → синхронный вызов блокирует запрос; таймаут настраивается в `services/ai.py`, ошибки превращаются в понятный HTTP-ответ, не ломая состояние песни.
- [Модель вернёт невалидный JSON/не по схеме] → строгая Pydantic-валидация отклоняет ответ, пользователь видит ошибку и может повторить запрос; данные песни не повреждаются.
- [JSONB-поля без миграции схемы хуков/секций может усложнить будущее расширение] → осознанный компромисс MVP согласно `AGENTS.md` (запрет дополнительных таблиц сверх `songs`/`messages`/`presets`); при необходимости будущие изменения смогут ввести отдельные таблицы отдельным change.
- [Удаление пресета, уже использованного в песнях] → `preset_id` в `songs` настроен как `ON DELETE SET NULL`, песня не удаляется и не теряет ранее скопированные значения анализа/настроек трека.
- [Рост объёма `messages` без ограничения] → вне скоупа MVP; при необходимости будущая доработка может добавить retention-политику.

## Migration Plan

- Новая функциональность разворачивается с нуля (кода ещё нет), миграция существующих данных не требуется.
- Порядок реализации зафиксирован в `tasks.md`: инфраструктура → auth/CRUD → пресеты → AI-сервис и роутер → frontend.
- Откат — остановка `docker compose` сервисов; постоянных данных, требующих отдельной стратегии отката, на момент MVP нет.
